# 物流园冷链车辆预约入场与温控异常协同服务

Java 17 + Spring Boot 3 + PostgreSQL 实现。覆盖「承运商预约 → 自动排入场窗口 → 闸口核验 →
月台卸货 → 质检抽样 → 隔离/处置 → 责任判定 → 结算扣罚/赔付 → 客户追溯」全链路，
承运商、园区调度、质检、客户客服、结算五类角色在**同一车次**上协同处理各类异常。

## 原始需求

开发物流园冷链车辆预约入场与温控异常服务，可使用 Java、Spring Boot 和 PostgreSQL。承运商提交车牌、司机、货主、货品类型、温区要求、预约时间、预计件数、车厢温度设备和电子封签后，服务根据月台容量、质检人员班次和客户优先级生成入场窗口。车辆到园时，闸口核验预约、车牌和封签，月台接车后上传开门前温度、卸货照片、破损件数和质检抽样结果。若车辆晚到、温度曲线断点、封签异常、货主临时改仓、月台拥堵或质检发现化冻，服务需要让承运商、园区调度、质检、客户客服和结算人员在同一车次中处理。货物放行、隔离、降级入库或拒收后，责任判断会影响承运商扣罚、客户赔付和后续预约优先级。服务还要保留温控设备原始数据、卸货时长和签收结果，便于客户追溯某批冷链商品的运输质量。服务还要兼顾多货主混装、夜间排队、司机证件过期、客户临时加急和园区限电。调度人员需要看到每辆车卡在闸口、月台、质检、隔离还是结算环节，客户客服则需要把温控异常解释成可理解的责任、货损和预计放行时间。

## 一键启动（宿主 docker compose）

```bash
cp .env.example .env        # CC_PUBLISH_PORT 由评测环境注入，默认 3094
docker compose up -d --build
# 健康检查
curl -s http://127.0.0.1:${CC_PUBLISH_PORT}/actuator/health
# 浏览器打开
open http://127.0.0.1:${CC_PUBLISH_PORT}/
```

- 仅 app 服务发布到宿主端口 `${CC_PUBLISH_PORT}:8080`；PostgreSQL **不发布宿主端口**，
  只在 compose 内网通过服务名 `db:5432` 访问。
- 多阶段 Dockerfile：`maven:3.9-eclipse-temurin-17` 构建，`eclipse-temurin:17-jre` 运行，
  非 root 用户 `appuser`，内置 `HEALTHCHECK`。
- 应用首次启动自动建表并写入演示数据（月台、货主、司机、账号、一辆多货主混装预约车）。

验证结束后：

```bash
docker compose down          # 如需清空数据库卷：docker compose down -v
```

## 推荐演示路径（约 5 分钟走通全部需求点）

1. `carrier1` 登录 → 预置车次 `鲁B12345`（海得鲜冻虾仁 200 件 + 晨光巴氏奶 100 件，**多货主混装**）
   已自动排窗；看板可见其落在「预约排窗」列。
2. `carrier1` 新提交一单，司机选择**李强（证件过期）** → 状态变「证件异常待换司机」，
   调度可在详情里「更换有效司机并重新排窗」。
3. `dispatch` 在详情点「回传失温曲线」（承运商也可）：自动检出**温度曲线断点**与**超温失温**两条异常；
   再点「闸口核验」演示：正常通过 / 晚到（自动记晚到异常）/ 封签不符拦截→人工放行。
4. 夜间到园车辆自动「夜间排队」，调度一键放行靠台；顶栏可「启动园区限电」，
   可用月台立即减半，在途车次自动挂限电异常。
5. 月台「接车卸货」→ 上传开门前温度/卸货照片/破损件数（卸货时长自动记录）。
6. `qc` 登录提交「发现化冻」→ 货物隔离，五类角色在同一车次异常区协同处理、留言。
7. `dispatch` 下处置结论：**逐货主**放行/降级/拒收；`cs_haixian` 可点「货主临时改仓」、
   「客户临时加急」，右侧面板给出可直接对客户讲的**责任比例/货损金额/预计放行时间**话术，
   并可打开「批次运输质量追溯」查看原始温度点、卸货时长、签收结果。
8. `settle` 登记签收并结算：生成结算单（承运商扣罚、客户赔付、园区补偿、服务分变动），
   服务分下降会影响该承运商**后续预约优先级**；车次进入「完成」。

## 排窗与判定规则（可在 `application.yml` 调整）

- 入场窗口 30 分钟，同月台窗口不重叠；温区精确匹配优先、通用月台兜底（混装按最冷温区）。
- 质检班次容量：白班（06:00–22:00）3 车/批，夜班（22:00–次日06:00）1 车/批；
  窗口若落夜班自动挂「夜间排队」提示。
- 优先级：`临时加急 > VIP > 标准 > 经济`，同档按承运商服务分排序；服务分<60 的非加急车顺延并预警。
- 晚到容忍 30 分钟；温度采样间隔 >20 分钟判「曲线断点」；温度超温区报警线判「失温」。
- 责任判定：到园前失温/断点/晚到/封签=承运商，拥堵/限电=园区，改仓=客户；
  「夜间排队+晚到」五五分，「限电期间化冻」承运商 70%/园区 30%；人工可在异常单改判。
- 结算：化冻件按货主赔付单价全损、破损件半损；拒收/降级再按责任比例追加违约金，
  同时扣减承运商服务分（影响后续预约）。

## 主要 HTTP 接口（均需 `X-Auth-Token` 登录头，`/api/auth/login` 除外）

| 方法 & 路径 | 角色 | 说明 |
|---|---|---|
| POST `/api/auth/login` | - | 账号密码换 token |
| GET `/api/appointments/board` | 全部 | 六环节看板（闸口/月台/质检/隔离/结算…） |
| POST `/api/appointments` | 承运商/调度 | 提交预约（多货主混装 lines），立即排窗 |
| POST `/api/appointments/{id}/gate-check` | 调度 | 核验预约/车牌/封签，判定晚到/夜间排队 |
| POST `/api/appointments/{id}/readings` | 承运商/调度 | 回传温控原始数据，自动断点/超温分析 |
| POST `/api/appointments/{id}/dock-start` `/unload` | 调度 | 靠台、开门前温度/照片/破损件数 |
| POST `/api/appointments/{id}/qc` | 质检 | 合格/化冻/拒收建议 |
| POST `/api/appointments/{id}/decision` | 调度/质检 | 放行/隔离/降级/拒收（支持逐货主） |
| POST `/api/appointments/{id}/warehouse-change` | 客服/调度 | 货主临时改仓 |
| POST `/api/appointments/{id}/urgent` | 客服/调度 | 临时加急重排 |
| POST `/api/appointments/exceptions/{exId}/handle` | 调度/质检/客服/结算 | 异常协同、改判责任、关闭 |
| POST `/api/appointments/power-shedding` | 调度 | 园区限电开关（月台减半） |
| POST `/api/appointments/{id}/settle` | 结算 | 签收+责任扣罚/赔付/服务分 |
| GET `/api/customer/appointments/{id}/explain` | 客服等 | 责任/货损/预计放行时间客户口径 |
| GET `/api/customer/appointments/{id}/trace` | 客服/承运商等 | 批次运输质量追溯（原始数据留存） |

## 技术说明

- 分层：`domain`（JPA 实体/枚举）、`repo`、`service`（排窗/温控分析/责任/结算/客服口径）、
  `web`（token 过滤器 + REST + 原生 JS 看板）。
- 温控设备原始采样点独立表全量留存（只追加、不覆盖），分析结论仅作异常与责任输入。
- 无前端构建、无外部 CDN，静态资源随 Jar 提供，断网环境可用。
